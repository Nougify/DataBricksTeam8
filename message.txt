# Backend contract: frontend requests (v2 draft)

This is the original contract with the frontend's requests added. Tags:

- **[CHANGED]**: an endpoint, object or event from the original contract that the frontend needs modified.
- **[NEW]**: something the frontend needs that isn't in the original.
- **[RETIRED]**: an original item replaced by something else. The replacement is named.
- Untagged text is unchanged from the original.

The frontend is a Next.js ops console for a TransLink dispatcher. It runs on `http://localhost:3001`. It shows a map of the 3 hubs, forecasts replayed against actuals, where people are coming from, and human-approved dispatch proposals. It also has a what-if planner, findings, and proof that the model works.

---

## Summary of requests

**Blocking: the demo can't work without these**

1. **An hourly forecast that is backtested over the replay period (Nov 2025 – Aug 2026).** Today `gold_hub_forecast` is daily-only and covers Sep–Oct 2026, which is outside the replay window. We need a table like `gold_hub_forecast_hourly(hub, issued_at, target_hour, lead_h, forecast, lower_80, upper_80)`. It must be built without future leakage, so a forecast issued at T only uses data before T.
2. **An hourly surge index with no look-ahead:** `surge_index = pings ÷ typical pings`. "Typical" means the same hub, day type and hour, averaged over trailing weeks before T. The existing daily `surge_index` in `gold_hub_daily` uses a centred ±4-week window, so it sees the future. That's fine for the timeline, but it must be labelled retrospective.
3. **Human approval for dispatches.** The engine proposes a trip, and the dispatcher approves or rejects it: new `POST .../approve` and `.../reject`, new trip status `PROPOSED`, new bus status `RESERVED`.
4. **Seek on the simulation clock** (`PUT /simulation/time`), so the UI can jump to any date and hour in the replay window with the date picker, presets and timeline scrubber.
5. **One shape per object.** `/state`, the list endpoints and WebSocket events must return identical Surge, Bus and Trip objects.

**Changes to existing endpoints:** conventions (§0), shared objects (§0.1), and sections 1–12 below.

**New endpoints (§13–§28, plus §8b, §9b, §11b):** meta, hubs, hub status, forecast, origins, timeline, events, route load, late-night, hourly profile, overview, route crowding, recommendations, findings, backtest, validation, seek, approve/reject, settings.

**Open questions for you:** at the end of this file.

## 0. Conventions [NEW]

- **Base path:** `/api/v1` for REST and `/api/v1/ws/simulation` for the WebSocket. The frontend reads both base URLs from env vars.
  - Note: today `backend/server.js` only serves `/api/health`.
- **CORS:** allow `http://localhost:3001` and `http://127.0.0.1:3001`. Make the list configurable (e.g. `CORS_ORIGINS`) so a Vercel domain can be added later.
- **Time:** ISO 8601 with the correct **America/Vancouver** offset for that date: `-08:00` in PST (Nov 2 2025 – Mar 8 2026) and `-07:00` in PDT.
  - Every hourly row **also** carries `local_date` (`"2025-12-06"`) and `hour` (0–23). The replay crosses both DST changes, so the frontend keys hourly buckets on `local_date` + `hour`, never on epoch math.
  - The hackathon table's `timestamp` has a `Z` suffix but is **local wall-clock time**. This was validated against TransLink ridership (r = 0.92). Don't convert it from UTC.
- **Hub ids:**

  | `hub_id` | `location_name` in the data |
  |---|---|
  | `ubc` | `UBC` |
  | `waterfront` | `Waterfront Station` |
  | `park-royal` | `Park Royal Mall` |

- **Day types:** `mf`, `sat`, `sun_hol`. The gold tables use `MF`, `Sat` and `Sun/Hol`.
- **Units:**
  - `pings` are integer device pings, not riders.
  - Any field ending in `_pct` is 0–100.
  - Indexes are ratios: `1.0` = typical, and `1.25` or more is a surge.
- **Route references** always carry both ids:
  - `route_id`: the GTFS `route_id`, exactly as in `routes.txt`.
  - `line_key`: the public line number used in the `hub_pulse` gold tables, e.g. `"99"`, `"R4"`.
- **Nulls:** send explicit `null`, never leave out a documented field.
- **Errors:** `{"error": {"code": "SOME_CODE", "message": "Human readable"}}` with a matching HTTP status. A 409 on a trip also includes the current `"trip"` object (see §9b).

## 0.1 Shared objects [NEW]

Every endpoint and WebSocket event that returns one of these objects returns **the full object in this exact shape**.

### RouteRef

```json
{
  "route_id": "6612",
  "line_key": "99",
  "short_name": "99",
  "long_name": "Commercial-Broadway / UBC (B-Line)",
  "mode": "Bus",
  "color": "#0060A9",
  "text_color": "#FFFFFF"
}
```

- `mode`: `Bus`, `SkyTrain`, `SeaBus` or `West Coast Express`.
- `color` and `text_color` come from GTFS `route_color`/`route_text_color`. If GTFS has none, they are `null`.
- All values above are examples.

### Clock (simulation)

```json
{
  "current_time": "2025-12-06T10:00:00-08:00",
  "local_date": "2025-12-06",
  "hour": 10,
  "speed": 60,
  "status": "PAUSED",
  "min_time": "2025-11-15T00:00:00-08:00",
  "max_time": "2026-08-31T23:00:00-07:00",
  "approval_mode": "MANUAL",
  "auto_pause_on_proposal": true,
  "epoch": 3
}
```

- `status`: `RUNNING` or `PAUSED`.
- `epoch` goes up by one on every seek (§8b). The frontend drops anything tagged with an older epoch.

### Surge [CHANGED]

```json
{
  "id": "surge-123",
  "hub_id": "ubc",
  "location_name": "UBC Exchange",
  "location": { "lat": 49.2606, "lon": -123.246 },
  "detected_at": "2025-12-06T10:00:00-08:00",
  "predicted_window": {
    "start": "2025-12-06T13:00:00-08:00",
    "end": "2025-12-06T15:00:00-08:00"
  },
  "lead_time_minutes": 180,
  "magnitude": {
    "predicted_pings": 4680,
    "typical_pings": 2610,
    "surge_index": 1.79,
    "lower_80": 4100,
    "upper_80": 5250
  },
  "severity": "HIGH",
  "drivers": [
    { "type": "EXAM", "label": "UBC December exam period", "event_id": "evt-ubc-exams-2025w1" }
  ],
  "predicted_destinations": [
    {
      "origin": "Surrey",
      "location": { "lat": 49.1897, "lon": -122.848 },
      "share_pct": 14.5,
      "expected_pings": 680
    }
  ],
  "status": "AWAITING_APPROVAL",
  "phase": "UPCOMING",
  "additional_trip_ids": ["trip-456"],
  "actual": null
}
```

What changed from the original:

- **New fields:**
  - `hub_id`: `null` when the surge is not at one of the 3 hubs.
  - `location_name`, `detected_at`, `lead_time_minutes`, `magnitude`, `severity`, `drivers`, `phase`, `actual`.
- **`predicted_time` is [RETIRED].** Use `predicted_window.start`.
- **`additional_trip_id` becomes `additional_trip_ids[]`.** One surge can need several buses.
- **`predicted_destinations[]`** gains `origin`, `share_pct` and `expected_pings`. These are the home/origin areas of the people in the surge, taken from the `origin` column, i.e. where they're likely to travel next.
- **`magnitude` numbers** describe the **peak hour** inside `predicted_window`.
- **`severity`:** `LOW` for 1.25–1.5, `MEDIUM` for 1.5–1.75, `HIGH` for 1.75 or more. Please publish the cut-offs in `/meta`.
- **`drivers[].type`:** `EXAM`, `HOLIDAY`, `SPORTS`, `CONCERT`, `FESTIVAL`, `NIGHTLIFE`, `WEATHER`, `OTHER`. The list is empty if nothing is known.
- **`actual`** stays `null` until `phase = RESOLVED`. Then it becomes `{"pings": 4912, "surge_index": 1.88}`. This lets the demo show that the prediction came true.

`status` describes the dispatch; `phase` describes time.

`status` values:

| Status | Meaning |
|---|---|
| `PENDING` | Detected; no proposal yet |
| `AWAITING_APPROVAL` **[NEW]** | At least one trip is `PROPOSED` |
| `DISPATCHED` | At least one trip was approved |
| `NO_MATCHING_ROUTE` | No route connects the surge to its destinations |
| `NO_BUS_AVAILABLE` | No spare bus can arrive in time |
| `EXPIRED` | The window started before any trip was approved |

If every proposal is rejected, the surge goes back to `PENDING` and the engine may propose an alternative. If none is possible, it becomes `NO_BUS_AVAILABLE`.

`phase` **[NEW]** values:

| Phase | Meaning |
|---|---|
| `UPCOMING` | Before the window |
| `ACTIVE` | Inside the window |
| `RESOLVED` | After the window; `actual` is filled |

```json
{
  "id": "bus-3",
  "status": "RESERVED",
  "location": { "lat": 49.25, "lon": -123.1 },
  "heading_deg": 245,
  "capacity": 77,
  "source": {
    "type": "ROUTE",

    "depot_name": null
  },
  "assigned_trip_id": null,
  "proposed_trip_id": "trip-456"
}
```

What changed from the original:

- **New fields:** `heading_deg`, `capacity`, `source`, `proposed_trip_id`.
- **`source`** says where the spare bus came from. This is the "low-demand route" in our pitch:
  - `type` is `ROUTE` or `DEPOT`.
  - When `type` is `DEPOT`, `route` is `null` and `depot_name` is set.
- **New status `RESERVED`:** the bus is held for a `PROPOSED` trip, so two proposals can't claim the same bus.

Bus statuses: `AVAILABLE`, `RESERVED` **[NEW]**, `DEADHEADING`, `WAITING`, `IN_SERVICE`, `RETURNING`, `REPOSITIONING`.

**Trip status → bus status [NEW]:**

| Trip status | Bus status |
|---|---|
| `PROPOSED` | `RESERVED` |
| `APPROVED` / `BUS_EN_ROUTE` | `DEADHEADING`, or `WAITING` once it reaches the surge stop |
| `IN_SERVICE` | `IN_SERVICE` |
| `COMPLETED` | `RETURNING`, then `AVAILABLE` |
| `REJECTED` / `EXPIRED` / `CANCELLED` | `AVAILABLE`, or `RETURNING` if it already moved |

Please confirm the table or send your own.

|---|---|

| `IN_SERVICE` | Running the extra trip |
| `COMPLETED` | Finished |
| `REJECTED` **[NEW]** | The dispatcher rejected it |
| `EXPIRED` **[NEW]** | Not approved before `approval_expires_at` |
| `CANCELLED` **[NEW]** | Approved, but later withdrawn by the engine, e.g. the forecast dropped below the threshold. Please send the reason in `rationale`. |

### What it is

Returns the **complete current simulation state**.

This is the main endpoint the frontend calls when it first loads. **[NEW]** The frontend also calls it after any `state.reset` WebSocket event, and after every WebSocket reconnect.

## 8b. `PUT /api/v1/simulation/time` [NEW]: seek

### What it is

Jumps the simulation clock to any time between `min_time` and `max_time`. The date picker, scenario presets, timeline scrubber, "Show me" links and "Reset demo" all use it.

### Input

```json
{ "current_time": "2025-12-06T10:00:00-08:00" }
```

### Behaviour

- The server rebuilds the state at T **deterministically**, so the same T always gives the same state:
  - Surges detected before T whose window hasn't ended are recreated.
  - Earlier approvals and rejections by the user are discarded.
  - Proposals whose window is still open come back as `PROPOSED` with a fresh `approval_expires_at`.
  - Buses are reset.
- Keeps the current `status` (paused or running) and `speed`.
- Increments `epoch`, then emits `state.reset` on the WebSocket.
- Returns 400 `OUT_OF_RANGE` if T is outside `[min_time, max_time]`.

### Output

```json
{ "...": "Clock (§0.1), with the new epoch" }
```

## 9b. `POST /api/v1/additional-trips/{trip_id}/approve` and `POST /api/v1/additional-trips/{trip_id}/reject` [NEW]

### What it is

Lets the dispatcher approve or reject a proposed trip, the human-in-the-loop step.

### Input

```json
{ "epoch": 3 }
```

For reject:

```json
{ "epoch": 3, "reason": "Driver shortage on route 25" }
```

### Behaviour

- **Approve and reject are processed one at a time.** An approve that races the expiry gets a clear answer.
- **Approving an already `APPROVED` trip returns 200,** so a double-click is safe.
- **Reject** releases the bus to `AVAILABLE`. The engine may then propose an alternative, which carries `replaces_trip_id` = the rejected trip.
- Each call emits `dispatch.approved` or `dispatch.rejected` on the WebSocket.

### Output

The updated AdditionalTrip (§0.1).

### Errors

409 responses include the current trip:

```json
{
  "error": { "code": "TRIP_EXPIRED", "message": "Proposal expired at 10:45 before it was approved." },
  "trip": { "...": "AdditionalTrip (§0.1)" }
}
```

| Code | When |
|---|---|
| `TRIP_EXPIRED` | The proposal expired first |
| `TRIP_REJECTED` | Approving a trip that was already rejected |
| `TRIP_NOT_PROPOSED` | Any other state conflict |
| `STALE_EPOCH` | The request's epoch is older than the server's (the user seeked meanwhile) |

## 11b. `PUT /api/v1/simulation/settings` [NEW]

### What it is

Holds settings that must live on the server so they don't race the clock at high speed.

At 3600x, 200 ms of network latency is 12 simulated minutes. So when a trip becomes `PROPOSED` and `auto_pause_on_proposal` is on, **the server** pauses the clock at that simulated instant. It then emits `simulation.state_changed` with `reason: "AUTO_PAUSE_PROPOSAL"`.

### Input

```json
{ "auto_pause_on_proposal": true }
```

### Output

```json
{ "...": "Clock (§0.1)" }
```

## 12. `WS /api/v1/ws/simulation` [CHANGED]

### What it is

WebSocket used to send **live simulation changes to the frontend**.

The frontend loads the initial state using:

```text
GET /api/v1/state
```

and then listens here for changes.

### What changed

- **[NEW] Envelope.** Every message is:

  ```json
  {
    "type": "surge.updated",
    "seq": 1043,
    "epoch": 3,
    "simulation_time": "2025-12-06T10:00:00-08:00",
    "data": { }
  }
  ```

  `seq` is strictly increasing across all message types.
- **[NEW] Full-object upserts.** Entity events carry the **whole** object from §0.1, not a partial one, so the frontend can just replace its copy.
- **[NEW] Rate limits:**
  - `simulation.tick` and `bus.positions_updated` at most 4 times per second of wall time. The frontend extrapolates in between.
  - Send positions in one batched message, not one message per bus.
- **[NEW] Reconnect:** the frontend reconnects with backoff, then refetches `/state`. No replay buffer is needed on the server.

### Events

| Type | `data` | Notes |
|---|---|---|
| `simulation.tick` **[NEW]** | `{ "current_time", "local_date", "hour" }` | 4/s or fewer |
| `simulation.state_changed` **[NEW]** | Clock (§0.1) + `"reason"` | `reason` is one of `PAUSED`, `RESUMED`, `SPEED`, `SETTINGS`, `AUTO_PAUSE_PROPOSAL` |
| `state.reset` **[NEW]** | `{ "epoch": 4, "reason": "SEEK" }` | Frontend refetches `/state` |
| `surge.updated` **[NEW]** | Surge (§0.1) | On create **and** every change (status, phase, actual). Replaces `surge.detected` |
| `dispatch.proposed` **[NEW]** | AdditionalTrip (§0.1) | Trip enters `PROPOSED`. Replaces `dispatch.created` |
| `dispatch.approved` **[NEW]** | AdditionalTrip (§0.1) | Trip enters `APPROVED` |
| `dispatch.rejected` **[NEW]** | AdditionalTrip (§0.1) | Trip enters `REJECTED` |
| `trip.updated` **[NEW]** | AdditionalTrip (§0.1) | Every other trip status change (`BUS_EN_ROUTE`, `IN_SERVICE`, `COMPLETED`, `EXPIRED`, `CANCELLED`) and progress. Replaces `trip.started` / `trip.completed` |
| `bus.updated` **[NEW]** | Bus (§0.1) | Status or assignment change |
| `bus.positions_updated` **[NEW]** | `{ "positions": [ { "bus_id", "location", "heading_deg", "status" } ] }` | Batched. Replaces `bus.position_updated` |
| `hub.demand_updated` **[NEW]** | HubStatus (§0.1) | Once per hub on each simulated hour boundary |

Every trip status change emits exactly one of `dispatch.proposed`, `dispatch.approved`, `dispatch.rejected` or `trip.updated`.

# Core Frontend Contract [CHANGED]

For the frontend, the core API can effectively be reduced to:

```text
GET  /meta                               Startup config, presets, thresholds        [NEW]
GET  /state                              Initial application state (+ after reset)  [CHANGED]
WS   /ws/simulation                      Everything that changes while running      [CHANGED]
PUT  /simulation/time | speed | settings Seek, speed, auto-pause                    [NEW/CHANGED]
POST /simulation/pause | resume          Play controls
POST /additional-trips/{id}/approve      Human approval                             [NEW]
POST /additional-trips/{id}/reject       Human rejection                            [NEW]
GET  /additional-trips/{id}              Detailed view / preview of a dispatch
GET  /hubs/{id}/forecast                 Actual vs forecast chart                   [NEW]
GET  /hubs/{id}/origins                  Where people are coming from               [NEW]
GET  /routes/load                        Need vs spare routes                       [NEW]
GET  /routes/{id}                        Existing TransLink route/schedule information
```

The other endpoints feed individual hub-panel tabs (`/timeline`, `/events`, `/hubs/*`, `/findings`, `/backtest`, `/validation`) or are for debugging (`/surges`, `/buses`, `/additional-trips`, `/simulation`).

**Priority if time is short:**

1. `/meta`, `/state` + WebSocket, seek, approve/reject, `/hubs/{id}/forecast` and `/hubs/{id}/origins`.
2. `/routes/load`, `/timeline`, `/hubs/{id}/hourly-profile`, `/hubs/{id}/late-night`, `/backtest`.
3. Everything else.

The frontend is built against mocks of this exact contract in the meantime.
